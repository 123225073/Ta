# Ta Windows v1.1.4 窗口生命周期对抗审查

审查日期：2026-08-28

## 结论

用户报告的三类故障均被真实复现，并且不是同一个表象问题：钉图失控来自不可逆的鼠标穿透；空历史后的“无反应”来自主进程与 React 路由失步；任务栏图标累积来自钉图原生窗口归属缺失和覆盖窗口反复创建。

## 修复前红灯证据

在隔离的临时用户数据目录中运行未修复 v1.1.3：

| 对抗项 | 修复前结果 |
|---|---|
| 清空全部历史后重新截图 | PNG 与索引重新写入，但结果页未渲染 |
| 钉图穿透后移回工具栏 | 仍保留 Windows `WS_EX_TRANSPARENT`，无法操作 |
| 钉图任务栏归属 | 没有工具窗口标记，也没有所有者窗口 |
| 连续 3 次截图/取消 | 新增 3 个覆盖窗口 |

对正在运行的安装版做只读 Win32 枚举时，也发现钉图是无所有者的可见顶层窗口，并带有鼠标穿透样式；这与“能看到悬停、却点不了按钮”和“任务栏多出 Ta 图标”完全一致。

## 第一性原理修复

1. 交互窗口必须始终保留一条可恢复路径。钉图移动改为图片指针事件到主进程的显式坐标链路；穿透窗口使用 `forward: true` 接收鼠标移动，光标重回工具栏时立即取消穿透。
2. 页面状态不能依赖浏览器是否把 hash 变化当成完整重载。主进程现在发送显式导航事件，结果对象与历史变更同时推送给现有 React 页面。
3. 同一显示器的截图覆盖层是可复用资源，不是一次性窗口。结束或取消时只隐藏并归还窗口池，通过 `captureId` 清空选区状态。
4. 钉图是主窗口拥有的工具窗口。即使主窗口隐藏，钉图仍显示；Windows 任务栏不会把每张钉图当成独立应用窗口。

## 修复后对抗结果

- 5 个测试文件、22 个单元测试通过。
- 3 轮完整 E2E 通过；每轮均覆盖真实桌面捕获、选区创建/移动/缩放、清空历史后恢复、钉图工具栏、钉图移动后的原生窗口坐标、穿透恢复、关闭、任务栏排除和窗口复用。
- 三轮覆盖窗口增长均为 0；截图框首次/连续可交互时间均低于 100 ms。
- E2E 全程使用临时用户数据目录，未删除或改写用户真实截图历史和 AI 配置。
- 生产依赖审计为 0 个已知漏洞；完整开发依赖审计受当前 `vitest@3` 与 `vite@8` peer 树不一致影响，未把该工具链问题伪装成安全结论。

## 仍然存在的边界

- Electron 的 GPU、网络和 renderer 子进程是正常多进程架构；它们不等于任务栏打开了多个软件。本次验收检查的是 Windows 顶层窗口归属和覆盖窗口创建计数。
- 鼠标穿透仍可通过托盘“恢复所有钉图交互”兜底；窗口内恢复是新增的主路径。
